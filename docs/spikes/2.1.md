# Spike 2.1: a real splat in three + Spark (world-viewer task 1)

Written 2026-11-16. The bare page is `tools/viewer-spike/index.html` (its own
`package.json`, not a workspace package; assets symlinked from `scratch/wl-1.1/`,
which is git-ignored). Run it with:

```
cd tools/viewer-spike && npm install
ln -sf ../../../scratch/wl-1.1/spz_100k.spz assets/splat-100k.spz   # and 500k likewise
python3 -m http.server 8790 --directory .
# http://127.0.0.1:8790/index.html?view=spawn|back|fit|nofix&lod=100k|500k&tint=1
```

The world is the `marble-1.1` kitchen recorded by Spike 1.1 the same day. Screenshots
were taken headless (Chrome for Testing, SwiftShader software WebGL) by a Playwright
script that waits for the page's LOADED status; the spawn view is saved as
`docs/spikes/2.1-spawn.jpg`.

## Answers

- **Versions:** `@sparkjsdev/spark` 2.4.0 with `three` 0.187.0 (Spark's peer range is
  three >= 0.180.0). Both load as ES modules; an import map to local `node_modules`
  works with no bundler. Spark is World Labs' own renderer.
- **The minimum scene:** `new SparkRenderer({renderer})` added to the scene, then
  `new SplatMesh({url})` (also `fileBytes`, `stream`, `onProgress`, `onLoad`). The mesh
  is a normal three object: position, quaternion and scale apply. `mesh.initialized`
  resolves when the file is decoded (76 to 359 ms here for the 100k and 500k files).
  `mesh.getBoundingBox(centersOnly)` exists and is how the numbers below were read.
- **Opacity and recolor: present.** `mesh.opacity` (number) and `mesh.recolor`
  (a `THREE.Color` multiplier) both take effect — the `?tint=1` view (recolor
  0.7/0.8/1.0, opacity 0.85) is visibly cooler and dimmer than the plain spawn view.
  So the haunt layer is not limited to the CSS overlay: dimming and a colour cast can
  be applied to the splats themselves. `onFrame({mesh, time, deltaTime})` also exists
  for per-frame modulation such as flicker.
- **LOD:** Spark has its own (`lod: true | "quality"`, `lodScale`, `maxSplats`), which
  is per-mesh level-of-detail inside one file, separate from choosing which SPZ file to
  download (`chooseLod`). Not measured here; the file choice remains the viewer's lever.
- **Orientation, scale, spawn: `poseFromService` is right.** With `upFix` [1,0,0,0]
  (quaternion half-turn about x), scale 1.438571, and the camera at
  [0, floorY + 1.6, 0] = [0, 0.185, 0] looking along -z, the kitchen stands upright
  and faces the cabinets exactly as the photo does (`2.1-spawn.jpg`: window left,
  cabinets centre, oven below, floor at the bottom of the frame with the floor grid
  on it). Without the fix the same camera sees the room inverted. Raw object bounds
  of the 100k file: centre (0.42, -0.01, -1.22), size (8.25, 2.08, 8.65) before the
  transform (the 500k file: centre (0.42, -0.02, -1.25), size (8.63, 2.36, 9.20)) —
  the room proper plus generated surroundings, at a plausible room scale once the
  metric scale is applied.
- **Collider:** the recorded `collider_mesh.glb` uses no glTF extensions at all
  (no `extensionsUsed`), so no Draco or Meshopt decoder is needed to load it.
- **Frame rate: not answered.** Under SwiftShader (software WebGL, this machine) the
  100k file ran at roughly 2 to 17 fps depending on capture timing and a 500k
  screenshot timed out at 30 s; none of that says anything about an integrated-GPU
  laptop or a phone. The manual perf checklist of world-viewer task 1 still needs
  real hardware, one number per LOD. The decorated FPS in the page is there for that run.

## What this settles for the build

- world-viewer tasks 3.2, 4 and 5 can use three 0.187 + Spark 2.4 as pinned here;
  the `initSplat` seam in `shared/src/viewer/loader.ts` is `SplatMesh` construction
  plus `initialized`.
- The manifest pose (orientation, scale, spawn, floor) needs no change.
- Default spawn defaults stand: eye 1.6 m over `floorY` at the origin, yaw 0.
